# M5 — Attachments: phase plan

Scope: file attachments on steps, objectives, activities and comments, with images pasted inline into descriptions and comments. Figma embeds and link attachments stay in `PLAN.md`'s "Later" row. Each phase ends in a proof run against the real thing, and the next phase starts from that verified state.

## End state

Anyone who can edit a step drops files on its panel. They show as a list (images as thumbnails that open full size), and the card shows a paperclip with a count. An image pasted or dropped into a description or a comment uploads and appears inline. Objectives and activities get a details panel with their description and attachments. A comment can carry files of its own. Files live in Postgres, so replicas, backups and the Helm chart need no new service. A read-only share link shows the images and offers the files.

## Decided with the user

| Question | Answer |
|---|---|
| Storage | Postgres. No object store |
| Size limit | 10 MB a file, configurable |
| File types | Any |
| What carries attachments | Steps, objectives and activities, and comments |
| Figma | Later, with link attachments |
| Display | A list in the panel, images inline in markdown, and a count on the card |

## Defaults chosen (change any of these before the phase that uses them)

| Area | Choice | Why |
|---|---|---|
| Tables | `attachments` holds the metadata: id, workspace, owner, name, content type, size, sha256, uploader, created, deleted. Its owner is exactly one of a step, a node or a comment (a `CHECK` on `num_nonnulls`). `attachment_data` holds the bytes (`bytea`), one row per attachment | Listing and counting never read file contents; one owner column per kind keeps foreign keys and cascades real |
| Size limit | 10 MB a file (Jira Data Center's default), set by `OMS_ATTACHMENT_MAX_MB`. No workspace quota; Settings shows the total size per workspace | Covers screenshots, PDFs and small exports; large designs and videos are better linked from where they live. Keeps the database, backups and memory per transfer small |
| File types | Any type is accepted (decided with the user). The server sniffs the type from the bytes and does not trust the browser | Teams attach logs, PDFs, zips and designs; sniffing keeps a renamed file from being served as something it isn't |
| Serving | `GET /api/workspaces/{slug}/attachments/{id}` sends `nosniff`, a private immutable cache and an ETag (the sha256). PNG, JPEG, GIF and WebP are sent inline; everything else, SVG included, as a download | SVG and HTML can run script; a download cannot |
| Markdown references | An inline image is saved as `![name](attachment:<id>)`. The renderer turns the id into the right URL: the workspace route in the app, the share route on a share link | Survives a renamed workspace and works on share links without rewriting text |
| Who can attach | Editors attach to steps and nodes and delete those files. Commenters attach to their own comments; a comment's files follow its edit and delete rules. Viewers and share links only read. API tokens: write tokens upload, read tokens download | The same rules as the thing the file is on |
| Comment drafts | Files added while writing a comment upload at once as pending files of the step, unseen by others. Posting the comment claims them. Pending files more than a day old are deleted by a sweeper (`SKIP LOCKED`, like webhooks) | A pasted image needs a URL before the comment exists |
| Deleting | A file is soft-deleted with Undo, like other deletes. It goes and comes back with its step, node or comment. A sweeper purges the bytes of files deleted more than 30 days ago | Matches undo everywhere else and keeps the database from only growing |
| Linked steps | Files belong to the step, so they show on every map the step is on | One step, one set of files |
| Events | `attachment.create` and `attachment.delete` go in history ("Olive attached spec.pdf to CHC-12"), the live feed and webhooks, with metadata only and never the bytes | Same path as every other change |
| Uploads | The body is the file's bytes as `application/octet-stream`, one file per request, with `?name=`; read through `MaxBytesReader` at the limit. The 1 MB JSON limit stays for everything else | A cross-site form can send multipart but not octet-stream, so the CSRF rule stays "no form-sendable bodies". Scripts use `curl --data-binary` |
| Exports | PNG and PDF exports show the card counts, not the files | Exports are pictures of the map |

Phase 1 notes:
- Migration `0017` adds `attachments` (owner columns for steps, nodes and comments, with the one-owner `CHECK`) and `attachment_data`, whose `bytea` column is stored out of line and uncompressed (`STORAGE EXTERNAL`), since most files are compressed already.
- Uploads moved from the planned multipart to a raw `application/octet-stream` body: multipart is one of the types a cross-site form can send, so allowing it would have needed a second CSRF rule.
- Files are reached only through a live step on a live map, so deleting a step hides its files and restoring brings them back with no change to the files themselves.
- Downloads send `Content-Security-Policy: default-src 'none'; sandbox` as well as `nosniff`, and only PNG, JPEG, GIF and WebP inline. Checked by making every file inline: the test fails on the HTML file.
- Memory, measured on the built server: eight parallel 10 MB uploads (four at a time) peaked at 130 MB resident, and eight parallel 10 MB downloads at 131 MB, from 36 MB idle. That fits the chart's 256Mi limit, so phase 6 leaves it.
- Webhooks offer `attachment.create`, `attachment.delete` and `attachment.restore`.

## Risks

- **Database size.** Files make the database, its backups and CNPG WAL grow. The 10 MB limit, the purge after 30 days and the usage figure in Settings make it visible and bounded; an object store backend can be added behind the same tables later if it becomes a problem.
- **Memory.** pgx reads `bytea` whole, and a transfer can hold two or three copies of the file, so a 10 MB file can take about 30 MB. Phase 1 caps concurrent transfers per replica (4 by default, with a queue), which keeps the peak near 120 MB, inside the chart's 256Mi limit. A parallel upload test in phase 1 measures the real peak; phase 6 raises the limit only if it shows the need.
- **Script in files.** Only raster images are ever sent inline, every response carries `nosniff`, and the app's CSP already blocks script from anywhere but itself.
