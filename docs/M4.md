# M4 — Connected: phase plan

Scope is the M4 row in `PLAN.md`: dependencies, linked maps, a REST API with tokens and an OpenAPI description, webhooks, and Mattermost. Each phase ends in a proof run against the real thing, and the next phase starts from that verified state.

## End state

A step can block other steps, across maps. The card shows "Blocked by CHC-7" while the blocker is open, and the map can draw the links. The same step can sit on several maps: edit it once, and every map shows the change live. A script, or another tool, uses the same API as the app with a token that an admin issued. It can read the API's description from an OpenAPI file. Changes go out as signed webhooks to any URL the workspace chooses, and as readable messages to a Mattermost channel. Failed deliveries retry, and an admin can see what was sent.

## What M3 already provides

- The event log records every map change with its actor, and a follower reads it by id (`internal/live`). Webhooks follow the same log.
- `DATA_MODEL.md` sketches `dependencies`, `api_tokens`, `webhooks`, `webhook_deliveries` and `integrations`.
- Placements already separate a step from where it sits; only the `(step_id, map_id)` uniqueness ties a step to one map in practice.
- Tokens are hashed at rest (`auth.NewToken`), as invites, resets and share links do.

## Defaults chosen (change any of these before the phase that uses them)

| Area | Choice | Why |
|---|---|---|
| Dependencies | "A blocks B", between any two steps of the workspace, on the same map or not. Editors add and remove them from the step panel (pick by key or title). A link that would make a cycle is refused | The mock-up's "Blocked by STORY-31" is the case people ask for; cycles have no useful meaning |
| Showing dependencies | A step with an unfinished blocker shows "Blocked by KEY" on its card. The panel lists Blocks and Blocked by. A "Lines" switch in the filter bar draws arrows between linked cards on the same map. It is off by default and kept per map in the browser | Badges carry the information; lines help planning but clutter a busy map |
| Linked maps | A step can be added to another map of the workspace from its panel ("Also on" → Add to a map, picking activity and release). It then has one placement per map. "Remove from this map" takes it off one map; "Delete step" deletes it everywhere and asks to confirm when it is on several | The placements table was designed for this; one step, one key, one history |
| Live updates for linked steps | A change to a step writes one event for each map it is on, so every open map gets it and every map's history shows it | The live hub already routes by map; fanning out at write time keeps it unchanged |
| API tokens | Admins issue tokens in workspace Settings: a name, read (viewer) or write (editor) scope, and an optional expiry. The token is shown once, then kept hashed with a visible prefix (`oms_ab12…`). Revoke any time; the list shows last use | Same pattern as share links; scopes map onto roles the API already checks |
| Using a token | `Authorization: Bearer oms_…` on the same `/api/workspaces/{slug}/…` endpoints the app uses, for that workspace only, and no account endpoints. No CSRF check, since there is no cookie. Changes made with a token show in history as "token CI bot" | One API, not two |
| OpenAPI | A hand-written OpenAPI 3.1 file in the repo, served at `/api/openapi.yaml`, with a link from Settings. A Go test fails when a route exists that the file does not describe, or the reverse | Generated specs from Go handlers need annotations everywhere; a test keeps the hand-written one honest |
| Webhooks | Admins add a URL, choose event types (for example `step.update`, `comment.create`) and get a secret. Each event is POSTed as JSON with an `X-OMS-Signature: sha256=…` HMAC header. Retries back off over about a day (1 min, 5 min, 30 min, 2 h, 12 h), then stop. The webhook's page shows recent deliveries with their status, and offers a "Send test" | The common shape (GitHub, Stripe); signatures let receivers trust the sender |
| Delivery across replicas | Deliveries are rows. Each instance claims due rows with `FOR UPDATE SKIP LOCKED`, so two replicas never send the same one twice | Works behind the HPA with no extra service |
| Webhook targets | Any http(s) URL, including private network addresses (a self-hosted install often posts to internal tools), except link-local and cloud metadata addresses (169.254.0.0/16, fd00:ec2::254). `OMS_WEBHOOK_BLOCK_PRIVATE=true` also blocks private ranges | LAN use is the point of self-hosting; the metadata endpoint is the classic SSRF target |
| Mattermost | An integration with a Mattermost incoming-webhook URL and a choice of events, posting one readable line per event ("Olive moved CHC-12 to Done on Launch plan", with a link) through the same delivery queue | Mattermost needs messages, not raw JSON; reusing the queue gives it retries for free |

Phase 1 notes:
- A dependency change is logged on every map either step is on, so each open map updates live and its history names the link. A status change on a step tells maps that only link to it (a `stepref` event), so "Blocked by" clears there too.
- The card badge names the first unfinished blocker and counts the rest (since replaced by a dependency mark on the card: red while a blocker is open, its tooltip lists both directions, and pressing it draws that step's lines); the panel's Dependencies section lists Blocked by and Blocks, opening steps on this map in place and steps on other maps on their own map.
- Lines are drawn over the grid from the cards' positions, red while the blocker is open and grey dashed once done. The switch shows only on maps that have links.
- Share links show links within the map only.

Phase 2 notes:
- A step goes on another map from its panel's On maps section: pick the map, then the activity and release there. Only maps using the step's workflow are offered, since the step keeps its status. "Remove from this map" takes it off one map (with undo); a step's last map cannot be removed that way.
- Changes to a step are logged on every map it is on. Copies are marked `echo` in the event log, so a step's history lists each change once, and webhooks (phase 5) can send each change once.
- Deleting an activity keeps its steps that are also on another map, hidden here until the activity is restored. Delete step deletes it everywhere; its confirmation says how many maps.
- Cards on several maps show a small link mark naming the other maps.

Phase 3 notes:
- Each token acts as its own bot user (`users.is_bot`), never a workspace member and with no password, so everything that records who did something (history, created-by, comments) names the token without new code paths. Its events record `actor_kind` `token`.
- A request with a bearer token uses only the token: a bad one is refused rather than falling back to the session cookie. Tokens skip the Origin check, since a browser never sends one on its own.
- Settings → API tokens (admins): name, Read or Read and write, expiry of 90 days, 30 days, a year or never; the token is shown once with Copy; the list shows prefix, creator, expiry and last use, and revokes.

UI changes made in this phase: the live connection icon is a plug (pulled out of its socket when offline); the map fills the window below the top bar and scrolls inside itself, so its scrollbars are always in view; the logo no longer wraps when the nav is crowded.

Map navigation (added between phases 3 and 4, at the user's request):
- Zoom scales the whole map from 50% to 150%: the − / % / + / Fit controls in the map's bottom-right corner, Ctrl+scroll (and trackpad pinches), and Ctrl+plus, minus and 0. It keeps the point under the pointer, or the middle of the view, in place. It uses CSS `zoom`, so scroll sizes, pinned rows, dragging and the dependency lines stay right; exports are always at 100%. Kept per map in the browser with the other view settings.
- Fit sizes the map to the room it has (not below 50%) and scrolls to its top left.
- Dragging empty space on the map pans it; cards, buttons, bands and fields keep their own drag and click.
- The objective and activity rows stay pinned at the top as a long map scrolls (a sticky subgrid sharing the map's columns), with their row labels as a frozen column on the left.
- A minimap above the zoom controls shows the whole map with the part in view outlined; click or drag in it to move there. It shows only when the map does not fit, and the Minimap button hides it.

Phase 4 notes:
- `api/openapi.yaml` (81 operations) was generated once from a table of the routes and their shapes, then kept as the hand-maintained source. The `api` package embeds it; the server sends it at `/api/openapi.yaml`.
- The server records each route as it registers it, so `TestOpenAPICoversRoutes` compares the real routes with the file's paths both ways (checked by renaming one path: it failed in both directions).
- CI lints the file with Redocly CLI 2.72.1 (pinned) on its recommended rules, less three it cannot meet by design: endpoints that cannot fail have no 4xx, the live feed answers 101, and that is noted in `redocly.yaml`.
- `TestOpenAPISchemasMatchStructs` holds each schema's field names to the Go struct the handlers send (checked by renaming one field). Field types and request bodies are not checked automatically; they were written from the handlers.

Phase 5 notes:
- Deliveries are queued inside `appendEvents`, in the event's own transaction, instead of by a separate follower reading the log: none can be missed or queued twice, and there is no cursor to keep. Echoes and `stepref` notes are skipped.
- Each server process runs a sender (`internal/webhook`) that claims due deliveries with `FOR UPDATE SKIP LOCKED` and a two-minute lease, so replicas never send one twice; checked with two senders and 30 deliveries.
- The address check runs in the dialer's `Control`, on the address actually connected to, so a name cannot resolve to a blocked address after it was saved. Redirects are not followed.
- Settings → Webhooks (admins): URL, Everything or chosen events, the secret shown once, an Active switch, Send test, and each webhook's deliveries with status, tries, result and next try, refreshing while open.

UI changes made in this phase: release bands fit the part of the map in view (and stay there when scrolled sideways or zoomed), less space around "+ Add release", and the theme toggle is a moon or sun icon.

Keycloak users (added between phases 5 and 6, at the user's request):
- SSO is any OIDC provider, set by `OMS_OIDC_*`; `docs/SSO.md` says how to point oh-my-story at an existing Keycloak realm. The LAN stack and the Helm chart pass the settings through.
- First and last name (`users.first_name`, `last_name`) and email follow the provider: refreshed at every SSO sign-in; display name is "First Last".
- With `OMS_OIDC_DIRECTORY=keycloak`, Members has "Add from Keycloak": search the realm through its admin REST API as the client's service account, pick a role, and the person is a member at once (account made or linked, identity pre-linked by their Keycloak id, which is their OIDC subject); no invite or email. They sign in with Keycloak and land in the workspace.
- Keycloak 26.8 accepts admin API tokens only with its `kc-admin-api` client scope (it adds the admin API audience); the dev realm sets it as a default scope on the client, and `docs/SSO.md` says to.

Phases 3 to 6 do not depend on 1 and 2 and could go first; dependencies and linked maps come first because they change what events say (step events fan out per map), which webhooks then send.

## Phase 6, Mattermost: on hold

The user is deciding whether they need it; M4 is otherwise done. The plan, as it stands, for when it is picked up:

- **What it does:** admins connect a Mattermost channel to a workspace, and changes post there as one readable sentence each with a link back, e.g. "**Jonathan Magtalas** moved **CHC-12** "Reset password" to **Done** on *Buddha* · open".
- **Settings → Mattermost** (admins): paste a Mattermost incoming-webhook URL, choose events, send a test. Several per workspace (a channel per team).
- **Built on webhooks:** a Mattermost integration is a kind of webhook, reusing the phase 5 queue, so it gets retries, delivery history, Send test, pause, and each change posted once. Only the body differs: a formatted message instead of JSON, no signature. Same address checks.
- **Wording:** one sentence per event type, in the words the map's History panel already uses (steps added, renamed, moved, finished, assigned; comments with the start of the text; dependencies; releases; steps put on another map), each linking to the step or map.
- **Default events:** step created, status changes, assignments, comments and new releases; reordering and colour changes off.
- **Out of scope:** Slack and Teams, anything coming back from Mattermost (slash commands, replies), and per-person notifications.
- **Proof:** Go tests format each event type to the expected sentence and link; Playwright points an integration at a stub receiver, changes a step and checks the message.
- **Open questions:** a real Mattermost in the LAN stack to try it (another service in `make lan-services`), or a stub for tests only; and whether the default events are right.
