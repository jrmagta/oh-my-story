# M1 — The map: phase plan

Scope is the M1 row in `PLAN.md`, plus password reset, which `API.md` defers to M1. Each phase ends in a proof run against the real thing, and the next phase starts from that verified state.

## End state

An editor creates a map with 3 or 4 backbone levels, builds the backbone, adds releases and stories, and drags stories between cells and releases. Opening a story shows its title, markdown description, status and assignee, all editable. Admins edit the workspace's status workflows. Two people on the same map see each other's edits and presence live, also when they are connected to different app replicas. Every change appears in the story's history and in the map's activity feed.

## Defaults chosen (change any of these before the phase that uses them)

| Area | Choice | Why |
|---|---|---|
| Write path | Every map write goes through one store function that runs the change, appends its `events` rows (changed fields only) and calls `pg_notify('events', id)` in the same transaction | No write can skip the log, which feeds sync, history and later webhooks |
| Ranks | Fractional keys generated in Go. Clients send the neighbours (`afterId`, `beforeId`), never rank strings | One implementation of the key scheme; clients reorder optimistically without computing keys |
| Reading a map | `GET` returns the whole map in one payload (statuses, nodes, releases, placements with their stories) and the id of the last event it includes | Maps hold hundreds of stories, not tens of thousands. One fetch plus events keeps the client simple |
| Writes | One REST endpoint per entity action, returning the updated entity | Small payloads, one event per call |
| Real-time | WebSocket at `GET /api/maps/{id}/live?after=<eventId>` using `github.com/coder/websocket`. Each instance holds one `LISTEN` connection. The server replays events after the given id, then streams live ones; if the gap exceeds 1000 events it sends `resync` | Reconnects resume without a reload; every replica behind the HPA sees every event |
| Client state | TanStack Query holds the map payload and events patch it in place. Zustand holds UI-only state: selection, drag, open panel | Both already in the stack |
| Conflicts | Last write wins per field. A move carries the `version` the client saw; a stale move still applies and the response says `stale: true` so the UI can warn | `DATA_MODEL.md`: versions detect, they do not reject |
| Presence | In memory per instance, shared through `pg_notify('presence', …)`, heartbeat every 30 s, entries expire after 75 s. Never stored | `DATA_MODEL.md` |
| Default workflow | Every workspace gets a "Default" workflow: To do, In progress, Blocked, Done. Migration `0002` adds it to existing workspaces; creating a workspace adds it | A map needs a workflow from the moment it exists |
| Map workflow | Chosen when the map is created and fixed in M1 | Switching means remapping every story's status; not needed yet |
| Deleting | Deleting a node soft-deletes its subtree and the stories placed under it. Restoring brings them back together | There is no backlog view in M1, so stories cannot be left without a place |
| Markdown | `react-markdown` without raw HTML; edit in a textarea with a preview | Safe by default, no sanitiser to maintain |
| Drag and drop | dnd-kit with pointer and keyboard sensors | Keyboard drags are accessible and easy to drive from Playwright |

## Phases

| # | Phase | Input state | Proof |
|---|---|---|---|
| 1 | **Schema and write path.** Migration `0002` per `DATA_MODEL.md` with the default-workflow backfill and the parent-level trigger. `internal/rank`. Store functions for maps, nodes, releases, stories (workspace key sequence), placements, workflows and statuses, all through the event-writing path | M0 | Go tests against Postgres: the trigger rejects wrong parent levels; `levels` cannot change once a node exists; story keys stay sequential under concurrent inserts; each mutation writes one event holding only the changed fields; rank keys sort between any two neighbours; deleting a status in use needs a replacement |
| 2 | **Map API.** REST endpoints for maps, nodes, releases, stories, moves, workflows and statuses; the map payload; role checks; `API.md` updated | 1 | Go HTTP tests: round trips for each entity; viewers and commenters read but cannot write; workflows need admin; ids from another workspace return `not_found` |
| 3 | **Map UI.** Map list on the workspace page; create a map with 3 or 4 levels; the map view per `map-v3.html` in both themes; inline add, rename and delete for objectives, activities, steps, releases and stories; the story panel | 2 | Playwright: build a 4-level map with a release and stories, edit a story's description and status, reload and see it unchanged; a viewer sees no edit controls |
| 4 | **Drag and drop.** Stories between cells, between releases and within a cell; nodes among siblings and steps to another activity; releases up and down. Optimistic, rolled back on error | 3 | Playwright pointer and keyboard drags that survive a reload; Go test for the stale-move flag |
| 5 | **Real-time sync and presence.** `LISTEN`/`NOTIFY` fan-out, the WebSocket with resume, the client applying events, presence avatars on the map | 4 | Go test: two servers on one database, a write through one reaches a socket on the other, and a reconnect with `after` replays what it missed. Playwright: two browser contexts see each other's edits without reloading, and each sees the other's avatar |
| 6 | **Custom status workflows.** Workspace settings: create and rename workflows; add, rename, reorder and recolour statuses and set their category; delete a status by moving its stories to another; pick the workflow when creating a map | 3 | Playwright: add a status, use it on a story, delete it and choose a replacement |
| 7 | **Audit history.** History tab on the story panel and an activity feed on the map, built from `events` with the actor and a readable change. Paged by event id | 5 | Go tests for paging and tenancy; Playwright: edit a story and see the change with its author in the history |
| 8 | **Password reset.** Request by email (always `204`, so it does not reveal accounts), single-use token valid for 1 hour, new password ends the user's other sessions | M0 | Go tests; Playwright through Mailpit |

Phases 6 and 8 do not depend on 4, 5 or 7 and can move earlier if useful.

Phase 6 notes:
- `/w/:slug/workflows` (nav: Workflows): everyone reads, admins change. Statuses reorder with up and down buttons rather than drag and drop: a short list, and buttons are simpler to use and test.
- Deleting a status always asks where its stories go, even when none use it; the API then reassigns whatever there is.
- No server changes: the workflow API from phase 2 covers it, and status changes already reach open maps live (as a reload).

Phase 5 notes:
- The hub never stops the server from starting. With CloudNativePG the migration Job runs after the app's pods are ready, so the app can start before its schema exists; the hub then keeps retrying, and since a missing event table means no events yet, it follows the log from id 0 once the table appears. (CI's CloudNativePG install caught the first version, which exited and deadlocked the install.)
- `internal/live` runs one hub per instance: one connection `LISTEN`s on `events` and `presence`, outside the pool. A notification only says "read on"; the hub follows the log by id, so a missed notification or a reconnect loses nothing. Each instance holds one extra Postgres connection for this.
- The socket subscribes before reading the backlog and skips ids it has sent, so an event written in between arrives exactly once.
- Presence is in memory per instance, announced through `pg_notify('presence', …)`: join, leave, and a beat every 30 s; entries expire after 75 s. A join from elsewhere makes each instance re-announce its own watchers of that map, so a newcomer sees everyone at once.
- Events now carry the entity's new `version` (and a placement move the story's), so a live client sends the right version with its next move. A version bump alone is still not a change.
- The client (`web/src/map/live.ts`) patches the cached map per event and reloads only on restores, workflow changes and `resync`. A reload can return a snapshot older than events already applied, so the last 500 events are kept and re-applied over it.
- Behind an ingress the socket needs WebSocket support (ingress-nginx has it); the 25 s ping keeps it under the usual 60 s idle timeout. `npm run dev` proxies the socket and rewrites its Origin.

Phase 4 notes:
- `web/src/map/moves.ts` holds the move rules as plain functions: what may drop where, which API move a drop means, and the map as it will look. `web/src/map/dnd.tsx` wires them to dnd-kit (core only; the sortable package was not needed).
- Dropping on a story means "next to it": after it when moving down its own list, before it otherwise. Dropping on a cell means its end; on the empty column under a node, its first child; on Unscheduled, the last release.
- Moves show at once with an interim sort key (a neighbour's rank plus U+0000, which sorts right after it). The server still computes every real rank; its reply replaces the interim one. A failed move puts the map back and shows the error; a stale story move applies and says so.
- Cards and node titles drag with the pointer from anywhere (after 6 px, so clicks still open and rename). Each also has a Move handle for the keyboard: Space to pick up, arrows to choose, Space to drop. Arrow keys skip the target the item is inside, so Up from the second card reaches the first card, not its cell. Targets that cannot take the item are disabled, so arrows only visit valid places; the item's own place stays enabled, so a drag starts over itself and dropping at once moves nothing.

Phase 3 notes:
- Routes: `/w/:slug/maps` lists maps; `/w/:slug/maps/:mapId` is the map, with `?story=<id>` for the open story so a reload or a shared link keeps it. The workspace index now opens maps.
- `web/src/map/layout.ts` turns the payload into grid columns and spans. An activity with no steps, or an objective with no activities, still takes a column, which holds the button for its first child.
- Every write refetches the map; phase 4 made moves optimistic and phase 5 patches the cache from events.
- Which add-node input is open lives in the map context: creating a first step turns the empty column holding the input into the step, and the input then reopens at the activity's own add button.
- Deleting a node or story offers Undo, which calls restore.

Phase 2 notes:
- Endpoints are in `API.md` under Maps. Story cells take story ids as anchors; the map payload keeps stories and placements as separate lists so a client can apply events to them one entity at a time.
- `GET` map reads in one repeatable-read snapshot, so `lastEventId` matches exactly what the payload contains.

Phase 1 notes:
- `store.write` is the only path that writes map data: it locks the map row (so neighbour-based rank keys cannot collide), runs the change, appends events and notifies with the id of the transaction's last event. A transaction-scoped advisory lock taken before the first event insert makes transactions commit in event-id order, so a reader following ids never skips one that commits late.
- Cascades write one event per affected row: deleting a node logs the node, its descendants and the stories on its steps; deleting a release logs a `move` for each placement sent to Unscheduled; deleting a status logs a status change for each reassigned story.
- A no-op update writes no event. Events leave out `version`.
- Positions in a cell name stories (`afterId`/`beforeId` are story ids); elsewhere they name the sibling itself.
- `oms_seed_workflow` (SQL) creates the standard four statuses, for the `0002` backfill, new workspaces and new workflows.

## Out of M1

Estimates, personas, labels, comments, search, filters and zoom are M2. A backlog view and linked maps are M4. Migration `0003` and later are not touched.
