# M2 — Planning: phase plan

Scope is the M2 row in `PLAN.md`: estimates and roll-ups, personas, labels, comments and @mentions, search, filter and highlight, saved views, zoom/collapse/focus. Each phase ends in a proof run against the real thing, and the next phase starts from that verified state.

## End state

An editor estimates steps and sees the totals per activity, objective and release. Steps carry labels; objectives carry the personas they serve. Anyone who can comment discusses a step in threaded comments, and an @mention emails the person named. Anyone finds a step across the workspace by key or words. On a map, a filter by label, status, assignee, persona, release or text either hides or dims what does not match; the filter can be saved by name, kept private or shared with the workspace, and sent as a link. Big maps zoom out to compact cards, collapse activities and releases, and focus one release.

## What M1 already provides

- `steps.estimate numeric(6,2)` and `workspaces.estimate_unit` exist; neither the step API nor the UI uses the estimate yet. `PATCH /api/workspaces/{slug}` already takes `estimateUnit`.
- `steps.search` (a `tsvector` over title and description, GIN-indexed) and the `pg_trgm` extension exist.
- The role model has a `Comment` action that commenters hold.
- The hub sends events without a `map_id` to every map in their workspace, so workspace-wide entities (labels, personas) reach open maps without hub changes.
- The mailer (`internal/mail`) sends through Mailpit in dev.

## Defaults chosen (change any of these before the phase that uses them)

| Area | Choice | Why |
|---|---|---|
| Migrations | One migration per phase that adds tables (`0004` labels, `0005` personas, ...), not one `0004` for all of M2. `DATA_MODEL.md`'s migration order is renumbered as they land | Schema lands with the code and tests that use it |
| Roll-ups | Summed in the browser from the map payload, not by a recursive CTE | The payload already holds every step and placement, and events keep it current, so totals stay live for free. A server-side roll-up can come with the public API in M4 if a consumer needs it |
| Estimates | A number from 0 to 9999.99, or none. Totals show the sum and how many steps have no estimate. The unit (`points`, `days`, ...) is a label set per workspace by admins | `DATA_MODEL.md` decision 2 |
| Labels | Workspace-wide. Editors pick labels on a step and create one by typing a new name. Admins rename, recolour and delete on a Labels settings page | Labels should mean the same on every map |
| Step labels in the log | A step's labels are a field of the step: a change logs a step `update` with `labelIds` before and after | History and live sync then need no new entity type |
| Personas | Workspace-wide, managed by editors on a Personas page (name, description, colour). Linked to objectives from the objective's header; shown as small badges there | `PLAN.md`: personas linked to objectives |
| Persona links in the log | A node `update` with `personaIds`, like labels | Same reason |
| Comments | Markdown, one level of replies, `commenter` and up. Authors edit and delete their own; admins delete any. Editors and the author resolve a thread. Deleting soft-deletes and shows "comment deleted" if it has replies | `DATA_MODEL.md` |
| Comment events | Entity `comment`, carrying the map of the step's placement so open maps get them live | A step sits on one map until linked maps in M4 |
| Mentions | Typing `@` offers workspace members. Each new mention emails that person once (not the author), sent after the commit like reset emails. No in-app inbox | Email already works; an inbox is a feature of its own |
| Search | `GET /api/workspaces/{slug}/search?q=`: an exact key match first, then prefix matches on the `tsvector`, limit 20, with each step's map and activity. Opened from the nav and with Ctrl+K | The index exists; a palette is quick to use and to test |
| Filter | Applied in the browser. Within one field, any value matches; across fields, all must. Highlight mode dims non-matching cards; hide mode removes them, and backbone columns stay so the map keeps its shape. The filter lives in the URL query, so a link shares it | No server work; links work before saved views exist |
| Saved views | Store the same filter JSON plus the mode. Anyone who can read the map saves private views; editors share them with the workspace. Listed in a menu in the map header | `DATA_MODEL.md` `saved_views` |
| Zoom, collapse, focus | Three card sizes (full, compact, title only), collapsible activities and releases, and focus on one release. Kept per map in the browser's storage, not on the server | These are personal view settings, not shared data |

Phases 2, 3, 6, 7 and 8 depend only on phase 1 and can be reordered if useful.

Phase 8 notes:
- All in the browser (`web/src/map/viewPrefs.ts`): card size, collapsed activities, collapsed release bands and the focused release, in `localStorage` under `oms-view:<mapId>`. Unreadable or missing storage falls back to the defaults and keeps changes for the visit. Everyone gets these controls, viewers included.
- Card size (Full, Compact, Titles) is a switch at the right of the filter bar. Compact hides labels, status and the comment count; Titles shows the title only.
- An activity collapses from its ⋯ menu to a 52 px strip with its name written vertically (click to open it out). Its cells show their step count and still take drops.
- A release band collapses with the ▾ before its name, keeping its counts and meter. Focus shows that band alone (Unscheduled too) and puts "Focus: name ✕" in the filter bar; focusing a release that was since deleted shows everything.
- Release bands no longer size the grid's columns (`width: 0; min-width: 100%`), so a narrow map (collapsed activities) wraps the band's contents instead of stretching the label column.

Phase 7 notes:
- Migration `0008` adds `comments` and `mentions`. Comment writes go through `store.write` on the step's map, so they are map events: the client bumps the step's `commentCount` on create and delete, and reloads open comment lists on any comment event.
- Store rules give `ErrForbidden` (403) where the role allows the route but not this row: editing someone else's comment, resolving another's thread as a commenter, or deleting another's comment below admin.
- Mentions: the client sends `mentionIds` for the members whose `@Display Name` is still in the text when posting; the server checks they are members, records them, and emails only those not mentioned on that comment before, never the author. Mail is sent after the reply, like reset emails.
- The step panel has Details, Comments (n) and History tabs. Typing `@` in a comment box lists matching members (arrows, Enter or Tab to pick); Ctrl+Enter posts. Cards show a comment count.

Phase 6 notes:
- No migration: it uses `steps.search` (a `simple` tsvector over title and description) from `0002`. Each query word becomes a prefix term (`word:*`) joined with `&`. Words are letters and digits only, so no tsquery syntax gets through. An exact key match ranks first, then `ts_rank`, then key.
- The palette (`web/src/pages/search.tsx`) opens with Ctrl+K or ⌘K anywhere in a workspace, or the Search button in the nav. It is a combobox over a listbox: arrows choose, Enter or a click opens the step's map with `?step=`, Escape or a click outside closes. Queries wait 150 ms after typing stops.

Phase 5 notes:
- Migration `0006` adds `saved_views`. Views are personal settings, not map content: no events, no live updates; the menu reloads the list when it changes and when the map reloads.
- The API validates the filter's shape and stores it re-encoded, with every list present. Ids inside are not checked, so a view naming a deleted label just matches nothing.
- Map handlers now see the caller's role (`mapRequest.role`) for rules that depend on it within one route: sharing needs editor, and admins may delete shared views.
- The Views menu opens the filter bar. Picking a view applies its filter, and the button names the view whose filter is on. With a filter on that matches no saved view, the menu offers to save it, with "Share with the workspace" for editors. A view's creator can share, unshare or delete it; admins can delete shared ones. Saving closes the menu.

Phase 4 notes:
- All in the browser; no server change. `web/src/map/filter.ts` holds the filter's shape, its URL encoding (`l`, `s`, `a`, `p`, `r` as comma-separated ids, `q` for text, `hide=1`) and the matching rules: any value within a field, every field across them. "Unassigned" and "Unscheduled" are the id `none`. Personas match through the step's objective.
- The filter is React state mirrored into the URL, not read back from it on each change: the router updates the URL asynchronously, so a controlled checkbox flicked back (a Playwright check caught it) and fast typing could drop characters.
- Dim (the default) fades non-matching cards; Hide leaves them out, and backbone columns and release bands stay. Totals, release counts and the status rings count matching steps only.
- The bar shows a chip per chosen value, the match count and Clear; Clear keeps the Dim/Hide choice.

Phase 3 notes:
- Migration `0005` adds `personas` (name unique ignoring case, description, colour) and `persona_nodes`. Nodes carry `personaIds` the same way steps carry `labelIds` (a subquery in `nodeCols`, replaced before the `UPDATE`); only objectives accept them.
- Editors manage personas, on the Personas page or by creating one from an objective's picker (the ☺ button among its tools). Badges show under the objective's title, with the description as a tooltip.
- The label picker became `TagPicker` (`web/src/map/TagPicker.tsx`), shared by labels and personas; inside a backbone card it keeps its own colours and opens to the right.
- Linking shows in the map's activity as "linked “Admin” to objective “Grow”". Deleting a persona unlinks it everywhere through one `persona` event, like labels.

Phase 2 notes:
- Migration `0004` adds `labels` and `step_labels`. Steps carry `labelIds` (sorted, never null), read with a subquery in `stepCols`. In `UPDATE ... RETURNING` that subquery sees `step_labels` as it was before the statement, so `UpdateStep` replaces the labels first.
- Roles: everyone reads labels, editors create them (from a step's picker or the Labels page), admins rename, recolour and delete them.
- The map payload includes the workspace's labels. Label events are workspace-wide and patched into open maps; deleting a label strips its id from steps on the client, as the server does, with no per-step events. A step's history therefore does not mention labels removed by deleting the label.
- The picker in the step panel: type to filter, Enter toggles an exact match (ignoring case) or creates a new label, which gets a palette colour picked from its name. Chips on cards and in the panel; the panel's chips have a remove button for editors.

Phase 1 notes:
- No migration: `steps.estimate numeric(6,2)` came with `0002`. The API takes a JSON number and rejects anything the column would round (more than two decimals) rather than storing a different value.
- `web/src/map/estimates.ts` sums in hundredths, so totals never show float drift. A step's total is its own steps; an activity's or objective's is everything under it. Totals say how many steps have no estimate, and are left out until something is estimated.
- Cards show the estimate in a ring coloured by status, as in the mock-up; long values stretch into a pill. Release bands show steps, the sum and a meter of done, in progress and blocked. The map header adds the map total.
- The unit is set on a new Settings page (name, key prefix, estimate unit), which only admins can change. Changing it does not reach open maps live: it is workspace data, not a map event.

## Out of M2

Public share links, PDF/PNG export and the roadmap view are M3. Dependencies, linked maps, the public API and webhooks are M4. An in-app notification inbox is not planned.

## Card interactions (after phase 5)

- Every card drags from anywhere: objectives, activities, steps and release bands, with the pointer (after 6 px, so clicks still work) or with the keyboard (focus it, Space to pick up, arrows, Space to drop). The separate ⠿ handles are gone. Presses inside an input or a `[data-no-drag]` element (menus, the date button) never start a drag.
- The keyboard handle is the title of a backbone card, the name of a release band, and the open button of a step card. It is not the whole card: a `role="button"` makes its content presentational, which hid the rename and add fields inside it.
- Space picks up and drops; Enter is left to the element, so it still opens a step.
- Objectives, activities and releases have a ⋯ menu that sits over the card's corner instead of beside the title, so titles keep the full width: Rename, Add activity and Personas… (objectives), Colour… (backbone cards), Delete. Rename turns the title into a field in the same font.

## Remodel after phase 1

Before phase 2 the map was remodelled (decided 2026-11-21):

- Every map has three levels: objectives, activities under them, and steps under activities. The 3- or 4-level choice and the backbone "step" column level are gone.
- What M1 called a story is now a step: a card in an (activity, release) cell with a key, title, description, status, assignee and estimate. The rename runs through the schema (`steps`, `placements.activity_id`), the API (`/steps`, `activityId`), events (entity `step`) and the UI.
- Step keys use the workspace's project key. Later (decided 2026-11-21) the key became three letters suggested from the workspace name ("Cheshire Cat" gives CHC), shown and editable when creating the workspace, and unique on the server (migration `0007`): a taken key is flagged with a free alternative.
- Personas link to objectives, not activities (phase 3).
- Migration `0002` was rewritten instead of extended, and the dev and LAN databases were reset; no other installs held data.
