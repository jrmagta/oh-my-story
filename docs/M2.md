# M2 — Planning: phase plan

Scope is the M2 row in `PLAN.md`: estimates and roll-ups, personas, labels, comments and @mentions, search, filter and highlight, saved views, zoom/collapse/focus. Each phase ends in a proof run against the real thing, and the next phase starts from that verified state.

## End state

An editor estimates stories and sees the totals per step, activity, objective and release. Stories carry labels; activities carry the personas they serve. Anyone who can comment discusses a story in threaded comments, and an @mention emails the person named. Anyone finds a story across the workspace by key or words. On a map, a filter by label, status, assignee, persona, release or text either hides or dims what does not match; the filter can be saved by name, kept private or shared with the workspace, and sent as a link. Big maps zoom out to compact cards, collapse activities and releases, and focus one release.

## What M1 already provides

- `stories.estimate numeric(6,2)` and `workspaces.estimate_unit` exist; neither the story API nor the UI uses the estimate yet. `PATCH /api/workspaces/{slug}` already takes `estimateUnit`.
- `stories.search` (a `tsvector` over title and description, GIN-indexed) and the `pg_trgm` extension exist.
- The role model has a `Comment` action that commenters hold.
- The hub sends events without a `map_id` to every map in their workspace, so workspace-wide entities (labels, personas) reach open maps without hub changes.
- The mailer (`internal/mail`) sends through Mailpit in dev.

## Defaults chosen (change any of these before the phase that uses them)

| Area | Choice | Why |
|---|---|---|
| Migrations | One migration per phase that adds tables (`0004` labels, `0005` personas, ...), not one `0004` for all of M2. `DATA_MODEL.md`'s migration order is renumbered as they land | Schema lands with the code and tests that use it |
| Roll-ups | Summed in the browser from the map payload, not by a recursive CTE | The payload already holds every story and placement, and events keep it current, so totals stay live for free. A server-side roll-up can come with the public API in M4 if a consumer needs it |
| Estimates | A number from 0 to 9999.99, or none. Totals show the sum and how many stories have no estimate. The unit (`points`, `days`, ...) is a label set per workspace by admins | `DATA_MODEL.md` decision 2 |
| Labels | Workspace-wide. Editors pick labels on a story and create one by typing a new name. Admins rename, recolour and delete on a Labels settings page | Labels should mean the same on every map |
| Story labels in the log | A story's labels are a field of the story: a change logs a story `update` with `labelIds` before and after | History and live sync then need no new entity type |
| Personas | Workspace-wide, managed by editors on a Personas page (name, description, colour). Linked to activities from the activity's header; shown as small badges there | `PLAN.md`: personas linked to activities |
| Persona links in the log | A node `update` with `personaIds`, like labels | Same reason |
| Comments | Markdown, one level of replies, `commenter` and up. Authors edit and delete their own; admins delete any. Editors and the author resolve a thread. Deleting soft-deletes and shows "comment deleted" if it has replies | `DATA_MODEL.md` |
| Comment events | Entity `comment`, carrying the map of the story's placement so open maps get them live | A story sits on one map until linked maps in M4 |
| Mentions | Typing `@` offers workspace members. Each new mention emails that person once (not the author), sent after the commit like reset emails. No in-app inbox | Email already works; an inbox is a feature of its own |
| Search | `GET /api/workspaces/{slug}/search?q=`: an exact key match first, then prefix matches on the `tsvector`, limit 20, with each story's map and step. Opened from the nav and with Ctrl+K | The index exists; a palette is quick to use and to test |
| Filter | Applied in the browser. Within one field, any value matches; across fields, all must. Highlight mode dims non-matching cards; hide mode removes them, and backbone columns stay so the map keeps its shape. The filter lives in the URL query, so a link shares it | No server work; links work before saved views exist |
| Saved views | Store the same filter JSON plus the mode. Anyone who can read the map saves private views; editors share them with the workspace. Listed in a menu in the map header | `DATA_MODEL.md` `saved_views` |
| Zoom, collapse, focus | Three card sizes (full, compact, title only), collapsible activities and releases, and focus on one release. Kept per map in the browser's storage, not on the server | These are personal view settings, not shared data |

## Phases

| # | Phase | Input state | Proof |
|---|---|---|---|
| 1 ✅ | **Estimates and roll-ups.** `estimate` in the story API, payload and events; an estimate field in the story panel and on cards; totals under each step, activity and objective, and per release in its band header; the unit on a workspace settings page | M1 | Go tests: estimate round trip, range checks, logged as a change. | 2 | **Labels.** Migration with `labels` and `story_labels`; label API (list, create, update, delete) and `labelIds` on story update; label picker in the story panel; chips on cards; Labels settings page | 1 | Go tests: tenancy, unique names ignoring case, deleting a label removes it from stories and logs it. | 4 | **Filter and highlight.** Filter bar on the map: labels, statuses, assignees, personas (through the story's activity), release, text over key and title. Highlight or hide. | 5 | **Saved views.** Migration with `saved_views`; API to list, create, rename, share and delete; menu in the map header | 4 | Go tests: private views are invisible to others, viewers cannot share. Playwright: save a view, open it as another member once shared |
| 6 | **Search.** The search endpoint; Ctrl+K palette; picking a result opens its map with the story panel open | 1 | Go tests: key match ranks first, prefix matches, deleted stories and other workspaces never appear. Playwright: find a story by a word in its description and land on it |
| 7 | **Comments and @mentions.** Migration with `comments` and `mentions`; comment API; Comments tab in the story panel with replies, edit, delete and resolve; a count on cards; `@` member picker; mention emails | 1 | Go tests: commenters comment but cannot edit stories; only authors edit; a mention emails once. Playwright: a commenter mentions someone, the mention arrives in Mailpit, a second browser sees the comment live |
| 8 | **Zoom, collapse and focus.** Card size switch, collapse buttons on activities and releases, focus a release, kept per map in browser storage | 1 | Playwright: collapse an activity and a release, switch to title-only cards, reload and see the same view |

Phases 2, 3, 6, 7 and 8 depend only on phase 1 and can be reordered if useful.

Phase 1 notes:
- No migration: `stories.estimate numeric(6,2)` came with `0002`. The API takes a JSON number and rejects anything the column would round (more than two decimals) rather than storing a different value.
- `web/src/map/estimates.ts` sums in hundredths, so totals never show float drift. A step's total is its own stories; an activity's or objective's is everything under it. Totals say how many stories have no estimate, and are left out until something is estimated.
- Cards show the estimate in a ring coloured by status, as in the mock-up; long values stretch into a pill. Release bands show stories, the sum and a meter of done, in progress and blocked. The map header adds the map total.
- The unit is set on a new Settings page (name, key prefix, estimate unit), which only admins can change. Changing it does not reach open maps live: it is workspace data, not a map event.

## Out of M2

Public share links, PDF/PNG export and the roadmap view are M3. Dependencies, linked maps, the public API and webhooks are M4. An in-app notification inbox is not planned.
